# Raft Distributed Consensus

Реализация алгоритма [Raft](https://raft.github.io/) на чистом Python — без единой внешней библиотеки. Пять сервисов поддерживают единый разделяемый JSON-объект с автоматическим выбором лидера и репликацией всех изменений.

## Что это такое

Raft — алгоритм распределённого консенсуса. Упрощённо: кластер из 5 нод ведёт себя как одна надёжная система. Все записи проходят через лидера, который реплицирует их на остальные ноды перед тем как подтвердить клиенту. Если лидер падает — остальные автоматически выбирают нового. Система остаётся доступной пока живы минимум 3 из 5 нод (кворум большинства).

## Технологии

- **Python 3.11+** — только стандартная библиотека
- `asyncio` — event loop, таймеры, конкурентность
- `http.server` + `ThreadingHTTPServer` — HTTP сервер
- `urllib.request` + `asyncio.run_in_executor` — асинхронные RPC-запросы между нодами
- `dataclasses` — типизированные модели данных

## Реализованные компоненты Raft

| Компонент | Описание |
|---|---|
| Leader Election | Term-based голосование. Кандидат побеждает набрав ≥3 голосов |
| Heartbeat | Лидер шлёт AppendEntries каждые 75ms. Таймаут фолловера 400–800ms (рандом) |
| Log Replication | Two-phase: append → ждём ACK от большинства → commit |
| `match_index` в ответе | Фолловер возвращает индекс до которого он синхронизирован — лидер сразу знает куда прыгнуть при откате, без декремента по одному |
| State Machine | Команды `set` и `delete` применяются к общему JSON-объекту |
| Proxy writes | Фолловер, получивший запись, проксирует её лидеру — клиент всегда получает результат |
| Safety | Нода голосует только за кандидата с логом не хуже своего (last_log_term, last_log_index) |

## Быстрый старт

### Запуск тестов
```bash
python run_tests.py
```

Тесты запускают все 5 нод in-process (без subprocess) и проверяют:

| # | Тест |
|---|---|
| 1 | Выборы лидера после старта |
| 2 | Запись и репликация на все 5 нод |
| 3 | Запись через фолловера (proxy) |
| 4 | Удаление ключа и его распространение |
| 5 | Убийство лидера → новые выборы |
| 6 | Запись после смены лидера |

## Настройка

Все параметры задаются через переменные окружения:

| Переменная | По умолчанию | Описание |
|---|---|---|
| `RAFT_NODE_ID` | `node1` | Идентификатор ноды |
| `RAFT_SELF_URL` | `http://127.0.0.1:8001` | Публичный адрес этой ноды (передаётся пирам) |
| `RAFT_HOST` | `0.0.0.0` | Адрес для прослушивания |
| `RAFT_PORT` | `8001` | Порт |
| `RAFT_PEERS` | `""` | Адреса остальных нод через запятую |
| `RAFT_ELECTION_TIMEOUT_MIN_MS` | `150` | Минимальный таймаут выборов |
| `RAFT_ELECTION_TIMEOUT_MAX_MS` | `300` | Максимальный таймаут выборов |
| `RAFT_HEARTBEAT_INTERVAL_MS` | `50` | Интервал heartbeat лидера |
| `RAFT_HTTP_TIMEOUT_S` | `0.1` | Таймаут RPC-запросов |

## Архитектурные решения

**Почему `asyncio` + `http.server`, а не FastAPI?**
Задание требует реализации без внешних библиотек. `asyncio` — стандартная библиотека Python. `http.server` — тоже. Raft-логика в asyncio, HTTP-сервер в отдельном потоке. Связь между ними через `run_coroutine_threadsafe`.

**`match_index` в `AppendEntriesResponse`**
При откате (follower отстал) лидер получает от фолловера точный индекс до которого тот синхронизирован и сразу устанавливает `next_index[peer] = match_index + 1`. Без этого лидер декрементировал бы `next_index` по одному — O(n) round-trips вместо O(1).
